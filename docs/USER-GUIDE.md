# راهنمای استفاده

راهنمای کامل GRE Tunnel Manager. برای دریافت و اجرای برنامه، ابتدا [شروع سریع](../README.md) را ببینید.

## راهنمای منوی اصلی

برای تنظیم تم، رنگ، چیدمان Guided/Compact و رفع مشکل نمایش، [راهنمای ترمینال](TERMINAL-UI.md) را ببینید.

| گزینه | کاربرد |
| --- | --- |
| 1: GRE Tunnel | ساخت، نمایش و حذف GRE/ip6gre و Simple GRE |
| 2: Port Forwarding | فوروارد با iptables یا nftables؛ افزودن، نمایش، ویرایش و حذف |
| 3: HAProxy Tunnel | افزودن، نمایش، ویرایش، حذف و تنظیمات HAProxy |
| 4: Realm Tunnel | افزودن، نمایش، ویرایش و حذف Realm |
| 5: Reverse Tunnel | تونل معکوس FRP یا rathole |
| 6: Load Balancing | تقسیم ترافیک بین چند سرور |
| 7: Settings & Tools | ظاهر، زبان، وضعیت سرور، بکاپ، پاک‌سازی و راهنما |

`Enabled` یعنی تنظیمات فعال است؛ به معنی تأیید دسترسی مقصد نیست.

## فوروارد مستقیم یا روی GRE

در **Port Forwarding**، گزینهٔ **Add iptables forward** یا **Add nftables forward** را انتخاب کنید. نام، پروتکل، IP همین سرور و پورت ورودی را بدهید. مقصد را مثل `203.0.113.20:443` وارد کنید؛ خط خالی پایان فهرست است. برای IPv6 از `[2001:db8::1]:443` استفاده کنید. وزن مقصد اختیاری است؛ مثلاً `203.0.113.20:443@2` یعنی وزن ۲.

برای استفادهٔ معمول، در سؤال **Advanced settings?** فقط Enter بزنید. هنگام ویرایش، انتخاب‌های قبلیِ interface و سیاست IP کلاینت حفظ می‌شوند. برای تغییر آن‌ها پاسخ `y` بدهید.

در حالت کرنلی، bind باید IP مشخص محلی باشد؛ `0.0.0.0` و `::` پذیرفته نمی‌شوند تا دامنهٔ اثر قوانین و هویت اتصال روشن بماند. پشت NAT ابری، IP محلی شبکهٔ سرور را بدهید.

برای WireGuard/AmneziaWG معمولاً UDP لازم است. برای Xray/sing-box پروتکل واقعی inbound تعیین‌کننده است. مدیر payload، UUID، handshake یا کلیدهای VPN مقصد را تفسیر نمی‌کند.

برای انتقال داخل GRE، ابتدا در **GRE Tunnel** روی دو سرور تونل بسازید. روی یکی **1: Kharej Server** و روی دیگری **2: Iran Server** را انتخاب کنید؛ این نام‌ها نقش دو سمت هستند و کشور سرورها می‌تواند متفاوت باشد:

- Kharej Server: آدرس `10.0.ID.1`؛ Iran Server: آدرس `10.0.ID.2`.
- شناسهٔ ۱ تا ۲۵۰ در دو سمت یکسان باشد.
- key، آدرس‌دهی و MTU پیش‌فرض ۱۴۳۰ با v13.7+ سازگارند.

در فوروارد، IP داخلی سمت مقابل را مقصد بدهید. routing لینوکس مسیر GRE را انتخاب می‌کند. حذف GRE تا وقتی تنظیمات جدید به رابط یا محدودهٔ آدرس داخلی آن ارجاع دارند متوقف می‌شود و ID وابستگی‌ها نمایش داده می‌شود؛ اتصال‌های غیرفعال هم بررسی می‌شوند. ابتدا آن اتصال‌ها را ویرایش یا حذف کنید. مسیرهای سفارشی و قوانین قدیمی/دستی را جداگانه بررسی کنید؛ شناسایی همهٔ وابستگی‌های شبکه ممکن نیست.

## حذف، ویرایش و بازیابی

فوروارد جدید ID مانند `F000001` دارد. برای حذف چند مورد، شمارهٔ ردیف‌ها را با فاصله بدهید: `1 3 4`. تمام اجزای متعلق به آن فورواردها از وضعیت مطلوب حذف و backend هماهنگ می‌شود.

قوانین قدیمی خودکار تصاحب نمی‌شوند. حذف گروهی در `Legacy forwarding`، خطوط شناخته‌شدهٔ مولد قدیمی را بر اساس پورت ورودی و مقصد گروه‌بندی می‌کند، TCP/UDP و تکرارها را حذف می‌کند و قواعد مشترک موردنیاز گروه‌های دیگر را نگه می‌دارد. خطوط دستی ناشناخته باقی می‌مانند.

پیش از تغییر وضعیت ذخیره‌شده، IP محلی، رابط انتخابی، forwarding موردنیاز IPv6 و قواعد تولیدشدهٔ iptables/nftables/HAProxy بررسی می‌شوند؛ Realm در این مرحله اعتبارسنجی داده و تولید تنظیمات دارد. سپس snapshot گرفته می‌شود. شکست اعمال، تلاش برای بازیابی وضعیت قبلی را فعال می‌کند. بازیابی تنظیمات، session قطع‌شده را زنده نمی‌کند. backup اسکریپت قدیمی دادهٔ اجرایی root است؛ فایل ناشناس را اجرا نکنید.

ویرایش، وضعیت فعال/غیرفعال و سیاست source IP را حفظ می‌کند. اگر همان اتصال در نشست دیگری تغییر کرده باشد، ذخیره متوقف می‌شود تا تغییر دیگری از بین نرود. IPv6های معادل، مقصد تکراری و حلقهٔ مستقیم به همان IP/پورت شناسایی می‌شوند. این کنترل‌ها جایگزین بررسی حلقه‌های چندمرحله‌ای یا مسیرهای نامتقارن نیستند.

## انتخاب موتور و تقسیم بار

| موتور | ترافیک | تقسیم بار | بررسی سلامت در این preset |
| --- | --- | --- | --- |
| iptables / nftables | TCP / UDP | weighted random برای اتصال جدید | ندارد |
| Realm | TCP / UDP | round robin / source hash | ندارد |
| HAProxy | TCP | round robin / leastconn / source / primary-backup | TCP check |
| FRP | TCP / UDP | گروه چند مقصد برای TCP | TCP check |
| rathole | TCP / UDP / هر دو | یک مقصد در هر instance | اتصال مجدد؛ بدون failover مقصد در این preset |

مقصدها را در خطوط جدا بدهید. `@2` یعنی وزن ۲. هر جریان NAT به مقصد انتخاب‌شدهٔ خودش متصل می‌ماند؛ تغییر مسیر، حفظ session را تضمین نمی‌کند.

چند پورت ورودی که به **یک IP و پورت نهایی** ترجمه می‌شوند، pool مستقل SNAT ایجاد نمی‌کنند. افزایش ظرفیت واقعی به ترکیب مقصد/مبدأ یا معماری بستگی دارد. تعداد کاربر برابر تعداد اتصال نیست.

## تنظیمات HAProxy

در **HAProxy Tunnel → Add tunnel** تونل TCP را بسازید. سپس **Tunnel settings** را باز کنید و تونل را انتخاب کنید. تغییرها تا `Save & apply` فقط در فرم هستند؛ `Cancel` آن‌ها را ذخیره نمی‌کند.

- **Balanced defaults**: مقادیر پایه؛ **Long-lived VPN**: timeout بی‌فعالیتی ۲۴ ساعت و لاگ فقط خطاها، با حفظ سایر انتخاب‌های فعلی.
- timeout اتصال به مقصد، بی‌فعالیتی دو طرف و انتظار در صف، جدا تنظیم می‌شوند.
- فاصله و timeout health check، تعداد شکست/موفقیت لازم و پورت بررسی مستقل قابل‌تنظیم‌اند. این check اتصال TCP را بررسی می‌کند؛ سلامت کامل Xray/Reality یا برنامهٔ مقصد را ثابت نمی‌کند.
- محدودیت کل اتصال و محدودیت هر مقصد، به همراه slow start برای بازگشت تدریجی مقصد وجود دارد. سقف بزرگ‌تر تضمین ظرفیت نیست و به RAM و فایل‌دسکریپتورها وابسته است.
- **PROXY v1/v2** فقط با پشتیبانی و تنظیم متناظر در مقصد روشن شود؛ پیش‌فرض خاموش است. این گزینه اطلاعات IP کلاینت را در یک هدر می‌فرستد؛ IP شبکهٔ اتصال خروجی همچنان متعلق به HAProxy است.
- وضعیت مقصد، تعداد session و صف از سوکت Unix با دسترسی محدود خوانده می‌شود. پنل HTTP یا پورت مدیریتی عمومی باز نمی‌شود. `socat` برای این کار و بررسی آماده‌شدن worker لازم است و همراه نصب جدید HAProxy پیشنهاد نصب می‌شود.
- تغییر سازگارِ تنظیمات با reload و تأیید PID worker جدید اعمال می‌شود. ارتقای سرویس قدیمی، تغییر محدودیت FD/اتصال یا تغییر موتور به restart نیاز دارد. حذف و غیرفعال‌سازی هم ممکن است اتصال‌های باز را پس از مهلت توقف قطع کنند. تضمین قطع‌نشدن در همهٔ شرایط ارائه نمی‌شود.

رکوردهای قدیمی نسخهٔ ۱ معتبر می‌مانند. ذخیرهٔ تنظیمات پیشرفتهٔ HAProxy یک رکورد نسخهٔ ۲ با گزینه‌های اعتبارسنجی‌شده می‌سازد؛ ویرایش، فعال/غیرفعال‌سازی و restore point این گزینه‌ها را حفظ می‌کنند. نسخه‌های قبلی مدیر قادر به خواندن این رکورد جدید نیستند؛ برای downgrade از snapshot مناسب استفاده کنید.

راهنمای جزئیات و امکانات بعدی مانند HTTP health check، TLS bridge، SNI و DNS در [HAProxy](HAPROXY.md) است. preset فعلی TCP passthrough است و TLS/REALITY سرویس مقصد را terminate نمی‌کند.

## حذف Legacy و تنظیمات سراسری

در **Settings & Tools → Cleanup** ابتدا نوع پاک‌سازی را انتخاب کنید. حذف کلی فقط فایل‌ها، unit و قواعد شناخته‌شدهٔ مولد قدیمی را می‌پذیرد و قبل از تغییر backup می‌گیرد. وجود دستور ناشناخته، unit سفارشی یا فایل نامعتبر، حذف کلی را متوقف می‌کند؛ برای حذف فورواردهای شناخته‌شدهٔ همان فایل از حذف گروهی استفاده کنید. حذف Simple GRE هم peer ذخیره‌شده و وابستگی‌های شناخته‌شده را بررسی می‌کند.

گزینهٔ ۱۰ قدیمی اکنون **Inspect legacy rules** است؛ محتوای فایل را می‌خواند و اسکریپت ذخیره‌شده را اجرا نمی‌کند. فورواردهای جدید را در بخش اصلی بسازید.

در **Legacy → 14: Performance** تنظیمات ظرفیت conntrack و TCP محلی، جدا و اختیاری‌اند. مقدار قبلی و مقدار اعمال‌شده در journal ثبت می‌شود. بازگردانی تنها مقداری را تغییر می‌دهد که هنوز برابر مقدار اعمال‌شدهٔ مدیر باشد؛ تغییر بعدی مدیر سرور حفظ می‌شود. راه‌اندازی GRE دیگر خودکار BBR، بافرها، conntrack یا IPv6 forwarding را بازنویسی نمی‌کند.

نصب قدیمی journal ندارد؛ گزینهٔ **Retire historical tuning files** فایل شناخته‌شده را backup و از اجرای مجدد در بوت خارج می‌کند، اما مقادیر قبلی runtime را حدس نمی‌زند. RPS، NOTRACK بدون برچسب و فایروال مشترک قدیمی ممکن است باقی بمانند و نیاز به بررسی جدا داشته باشند. حذف چند منبع، تراکنش اتمیک نیست؛ خطای جزئی با نگه‌داشتن فایل و backup گزارش می‌شود.

## ارتباط معکوس و WSS

ابتدا در `Reverse Tunnel` موتور را انتخاب کنید. توضیحات این بخش برای **FRP** است:

روی سرور عمومی `Set up entrance` و روی هر مقصد `Set up destination` را اجرا کنید. token، control port، public port و transport هماهنگ باشند. برای چند مقصد TCP، group و group key یکسان و نام connection هر مقصد متفاوت باشد.

- TCP Mux در این نسخه stream multiplexing در FRP است؛ HTTP CONNECT proxy type با نام `tcpmux` نیست.
- TCP و WS از TLS داخلی FRP استفاده می‌کنند؛ QUIC هم رمزنگاری دارد. این presetها token authentication دارند؛ CA اختصاصی برای آن‌ها تنظیم نشده است.
- **WSS** از HAProxy TLS در ورودی استفاده می‌کند. PEM شامل chain و private key را زیر `/etc` آماده کنید. FRP ورودی فقط روی loopback و پورت داخلی جدا می‌شنود. مقصد فایل CA/گواهی مورداعتماد می‌خواهد؛ SAN گواهی باید IP ورودی را پوشش بدهد. تمدید گواهی و restart درگاه بر عهدهٔ اپراتور است.
- control port و public port باید در فایروال میزبان/دیتاسنتر مجاز باشند. در QUIC کانال control از UDP استفاده می‌کند؛ پروتکل عمومی سرویس انتخاب مستقلی است.

دانلودهای جدید Realm v2.9.6 و FRP v0.71.1 با SHA-256 مشخص برای amd64/arm64 pin شده‌اند. باینری موجود خودکار ارتقا داده نمی‌شود؛ نسخهٔ آن را بررسی کنید. HAProxy از بستهٔ توزیع نصب می‌شود.

## ارتباط معکوس با rathole

در `Reverse Tunnel → rathole` روی ورودی `Set up entrance` و روی مقصد `Set up destination` را اجرا کنید. نام اتصال، پروتکل، پورت کنترل و token یکسان باشند. ورودی یک کلید Noise تولید می‌کند؛ فقط **کلید عمومی** نمایش‌داده‌شده را از مسیر مورداعتماد به مقصد منتقل کنید. کلید خصوصی و token در فایل تنظیمات با دسترسی ۶۰۰ می‌مانند و در آرگومان پردازش قرار نمی‌گیرند.

این preset از Noise NK روی **TCP** استفاده می‌کند. انتخاب UDP یعنی دیتاگرام UDP داخل این اتصال TCP منتقل می‌شود؛ در مسیر پرتلفات ممکن است تأخیر ایجاد شود. QUIC و تقسیم بار rathole در این preset نداریم؛ برای گروه مقصد از گزینه‌های FRP یا HAProxy متناسب با سناریو استفاده کنید.

نصب اختیاری rathole **0.5.0** با SHA-256 ثابت است: x86_64 با بستهٔ GNU/Linux و aarch64 با musl. ابزارهای `curl unzip sha256sum install` لازم‌اند. باینری موجود با نسخهٔ ناسازگار جایگزین نمی‌شود. نام موجود هم بازنویسی نمی‌شود. `List / remove` فقط سرویس و تنظیمات instance انتخاب‌شده روی همین سرور را حذف می‌کند؛ سمت مقابل جدا مدیریت می‌شود. FRP و rathole فعلاً خارج از restore point فورواردهای TSV هستند.

## فارسی در ترمینال

Bash متن UTF-8 چاپ می‌کند؛ اتصال حروف و راست‌به‌چپ به terminal emulator بستگی دارد. ابتدا `Test Farsi display` را ببینید. فارسی فقط برای راهنماهای مستقل است؛ IP، پورت، فرمان و عنوان‌ها چپ‌به‌راست می‌مانند. اگر نامرتب بود، Finglish را انتخاب کنید. متن معکوس یا reshape نمی‌شود.

## محدودیت‌های عملیاتی

- nftables فقط `inet gre_manager` را تغییر می‌دهد. ACCEPT آن، DROP در base chain دیگرِ UFW/Docker را خنثی نمی‌کند؛ سیاست میزبان را بررسی کنید.
- iptables فقط chainهای `GTM_*` را مدیریت می‌کند؛ کل فایروال flush نمی‌شود.
- nftables برای جریان TCP متعلق به مدیر، MSS بستهٔ SYN را با توجه به مسیر خروجی محدود می‌کند و مقدار کوچک‌تر اعلام‌شدهٔ کلاینت را افزایش نمی‌دهد؛ برای UDP و MTU ناشناخته راه‌حل خودکار نیست.
- IPv6 NAT به routing آماده نیاز دارد؛ مدیر بدون اطلاع IPv6 forwarding و RA را تغییر نمی‌دهد.
- interface ورودی در فوروارد کرنلی اعمال می‌شود؛ برای رله‌ها در این نسخه پشتیبانی نمی‌شود.
- مقصد جدید باید IP باشد؛ hostname، IPv4-mapped IPv6 و scope ID پذیرفته نمی‌شوند.
- نصب link جدید WireGuard/AmneziaWG و GRE over UDP هنوز اضافه نشده؛ فوروارد ترافیک آن‌ها پشتیبانی می‌شود.
- tuning جدید اختیاری و دارای journal است؛ تنظیمات تاریخی بدون مقدار قبلی ثبت‌شده خودکار به «پیش‌فرض حدسی» برنمی‌گردند.

## بررسی و عیب‌یابی

پس از دریافت `gre.sh`، این فرمان‌ها وضعیت یا تنظیمات را بدون اعمال تغییر بررسی می‌کنند:

```bash
bash gre.sh --version
sudo bash gre.sh --validate
sudo bash gre.sh --plan
sudo bash gre.sh --doctor
sudo bash gre.sh --haproxy-status F000001
bash gre.sh --catalog
```

`F000001` را با شناسهٔ اتصال خود جایگزین کنید. `--validate` ساختار و تداخل تنظیمات را بررسی می‌کند؛ `--plan` تنظیمات تولیدشده را نشان می‌دهد و `--doctor` وضعیت ابزارها، مسیرها و سرویس‌ها را می‌خواند. این فرمان‌ها آزمون سلامت کامل مقصد یا سنجش سرعت نیستند. خروجی plan شامل آدرس‌ها و توپولوژی است.

برای بررسی یک کپی تنظیمات، از `bash gre.sh --plan --state-file ./connections.tsv` استفاده کنید. جزئیات بازیابی در [Operations](OPERATIONS.md) آمده است.
